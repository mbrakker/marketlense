# Cross Report Publishing Delivery Plan (No Metrics Normalization)

Last updated: 2026-05-13
Scope: design + implementation sequence for cross-report report publishing capabilities, explicitly excluding metric normalization.

---

## 1) Objective

Deliver a production-ready **cross-report publishing capability** that can:

1. ingest and store report-level and entity-level outputs already generated by the pipeline,
2. automatically choose a thematic angle per cross report,
3. synthesize multi-report narratives with evidence traceability,
4. support cross-report search and retrieval,
5. introduce **signal-centricity** as a first-class ranking dimension on top of today’s report-level eccentricity tendencies,
6. publish cross reports with governance and observability equivalent to current single-report publishing.

Constraint: **No metric normalization** in this phase. Numeric metrics can be extracted and referenced as-is with provenance; do not attempt cross-source unit harmonization/conversion.

---

## 2) Current State (What Exists Today)

### 2.1 Pipeline and publish model are report-centric

- The orchestrated flow is mature for **single report -> analysis -> HTML -> WordPress publish**.
- Report generation, validation, render, and publish have strong contracts and orchestration boundaries.
- Publishing is primarily per-report (single source artifact promoted to WP post).

### 2.2 Strong foundation for future cross-report analytics already exists

A post-analysis projection layer exists and is explicitly framed as a foundation for future cross-report analytics:

- projected relational tables (`report_sections`, `report_findings`, `report_metrics`, `report_quotes`, `report_claims`, `report_tags`, `report_categories`, `report_figures`),
- `vector_projection_queue` for future embedding workflows,
- projection orchestrator that runs after report generation and stores non-blocking projection failures.

### 2.3 There is no full cross-report product workflow yet

The foundation intentionally does **not yet** provide:

- global cross-report retrieval product path,
- thematic automatic clustering/selection,
- multi-report synthesis/publishing workflows,
- signal-centric ranking objective,
- operator-facing cross-report curation lifecycle.

### 2.4 Taxonomy and evidence are available but still report-bounded in operation

- Report-level taxonomy extraction and evidence packs are available and useful as seed signals.
- Current outputs can support cross-report composition, but orchestration and storage are not yet organized around cross-report "bundle" entities.

## 3) Target End State (Top-Tier System, Without Metrics Normalization)

### 3.1 New product primitive: Cross Report Bundle

Introduce a first-class entity: `cross_report_bundle` (versioned contract + persistent store rows), representing:

- topic/theme label,
- selected source reports,
- synthesis artifacts (summary, key signals, disagreements, confidence notes),
- provenance graph (claim -> source report -> evidence span/table/quote id),
- lifecycle state (`draft`, `validated`, `ready_to_publish`, `published`, `superseded`).

### 3.2 Signal-centric intelligence layer

Add a deterministic and model-assisted signal layer that prioritizes:

- novelty/importance signals,
- recurrence/convergence signals across sources,
- contradiction/tension signals,
- recency/coverage signals,
- source reliability priors (policy-driven).

This layer should rank report fragments and claims for synthesis while preserving source wording/units (no normalization).

### 3.3 Cross-report search and retrieval

Provide dual-mode retrieval:

1. **lexical/structured search** over projected SQLite entities,
2. **vector semantic retrieval** over embedded entities from `vector_projection_queue` workers.

Search returns evidence-bearing chunks with explicit metadata filters (publisher, date range, domain tags, geography, content class).

### 3.4 Thematic automatic choice

Automate theme selection per publish cycle from available candidate signals:

- demand signals (recent report density + query patterns),
- novelty signals (new vs prior bundles),
- editorial policy constraints,
- quality thresholds (minimum corroboration and source diversity).

### 3.5 Cross-report synthesis + publishing

A dedicated cross-report generator/orchestrator stack should:

- choose theme,
- select report set,
- retrieve evidence,
- build synthesis with explicit uncertainty,
- run schema + policy validation,
- render and publish to WordPress as a distinct post type or taxonomy-targeted variant.

### 3.6 Governance and reproducibility

Same standards as current pipeline:

- typed contracts,
- structured logs (`run_id/task_id/span_id/role/module`),
- typed errors + retry policy in orchestrators,
- idempotency keys,
- replayability and artifact traces,
- CI gates and integrity tests.

---

## 4) Gap Analysis (Current -> End State)

### Gap A: Data model gap
No canonical cross-report contracts or persistence entities for bundle lifecycle, synthesis evidence graph, or signal-level scoring.

### Gap B: Retrieval gap
Projection tables exist, but there is no production retrieval service that unifies SQL filtering and semantic vector retrieval for cross-report composition.

### Gap C: Theme-selection gap
No automatic thematic chooser with deterministic policy + explainable scoring.

### Gap D: Synthesis gap
No dedicated multi-report synthesis generator with anti-hallucination constraints and claim-to-evidence enforcement across reports.

### Gap E: Signal-centricity gap
No explicit "signal-centric" ranking framework layered above current report-level outputs; no cross-report signal ledger.

### Gap F: Publish workflow gap
No cross-report orchestrator/publish pipeline, lifecycle states, or WP integration contract for cross-report artifacts.

### Gap G: Operability/test gap
No full test matrix for cross-report path (contracts round-trip, retrieval correctness, synthesis failure paths, idempotent republish behavior, quality regression packs).

## 5) Consolidated TODO (Implementation Sequence)

> Format: **Task / Why / Deliverables / Acceptance Criteria / Dependencies**

## Phase 0 — Architecture, contracts, and migration plan

### Task 0.1 — RFC + bounded-context map for cross-report capability
- **Why:** Prevent role mixing and avoid fragmented ad-hoc modules.
- **Deliverables:** design doc defining contracts/services/generators/orchestrators boundaries, import rules, and extraction policy.
- **Acceptance Criteria:** approved architecture doc with explicit non-goals (including no metrics normalization).
- **Dependencies:** none.

### Task 0.2 — Versioned cross-report contract family
- **Why:** Create canonical typed interfaces before coding logic.
- **Deliverables:** dataclasses for bundle request/response, theme candidate, retrieval hit, signal score, synthesis output, publish request/result.
- **Acceptance Criteria:** schema_version present, serialization round-trip tests pass.
- **Dependencies:** 0.1.

### Task 0.3 — Storage migration strategy
- **Why:** Ensure additive rollout with rollback.
- **Deliverables:** migration ledger entries + new tables for bundles, bundle_sources, bundle_signals, bundle_claims, bundle_publish_history.
- **Acceptance Criteria:** idempotent migrations + downgrade plan documented.
- **Dependencies:** 0.2.

## Phase 1 — Storage and retrieval foundation

### Task 1.1 — Analytics store extension for cross-report entities
- **Why:** Persist bundle lifecycle and provenance independently from per-report tables.
- **Deliverables:** service methods for upsert/get/list bundle entities with typed contracts.
- **Acceptance Criteria:** integration tests for create/update/reload and stale-row cleanup scoped by bundle_id.
- **Dependencies:** 0.3.

### Task 1.2 — Vector queue worker for cross-report retrieval readiness
- **Why:** Activate semantic retrieval path from existing queue foundation.
- **Deliverables:** worker orchestrator/service for embedding pending queue rows; retry taxonomy; status transitions.
- **Acceptance Criteria:** pending->embedded/failed transitions logged and tested; idempotent re-runs.
- **Dependencies:** 1.1.

### Task 1.3 — Cross-report search service (SQL + vector)
- **Why:** Unify structured filtering and semantic search as one canonical boundary.
- **Deliverables:** `cross_report_search_service` with query contracts, filter grammar, ranking merge policy.
- **Acceptance Criteria:** deterministic ranking given fixed inputs; latency budget met on fixture corpus.
- **Dependencies:** 1.1, 1.2.

## Phase 2 — Signal-centric layer

### Task 2.1 — Signal ontology and scoring policy
- **Why:** Make signal-centricity explicit and explainable.
- **Deliverables:** YAML-configured signal types, weights, thresholds, and fallback behavior.
- **Acceptance Criteria:** policy loaded via config service; invalid policy fails fast with typed AppError.
- **Dependencies:** 0.1.

### Task 2.2 — Signal extraction generator
- **Why:** Derive signal rows from projected findings/claims/quotes/tags.
- **Deliverables:** generator producing `CrossSignalSet` dataclass with per-signal provenance.
- **Acceptance Criteria:** required fields non-empty; failure-path tests assert error taxonomy.
- **Dependencies:** 1.1, 2.1.

### Task 2.3 — Signal-centric ranking engine (no metric normalization)
- **Why:** Rank evidence for synthesis by multi-signal utility, not raw numeric comparability.
- **Deliverables:** deterministic ranking utility + generator integration.
- **Acceptance Criteria:** tests prove ranking stability and explainability logs.
- **Dependencies:** 2.2.

## Phase 3 — Thematic automatic choice

### Task 3.1 — Theme candidate builder
- **Why:** Generate candidate themes from taxonomy + signal clusters.
- **Deliverables:** generator that outputs theme candidates with source-coverage stats.
- **Acceptance Criteria:** min coverage/diversity constraints enforced.
- **Dependencies:** 1.3, 2.3.

### Task 3.2 — Theme selector policy orchestrator step
- **Why:** Choose one theme deterministically with optional LLM tie-break.
- **Deliverables:** orchestrator stage with logging of scored candidates and selection reason.
- **Acceptance Criteria:** repeated runs with same input select same theme (unless tie-break explicitly enabled and seeded).
- **Dependencies:** 3.1.

## Phase 4 — Cross-report synthesis

### Task 4.1 — Prompt namespace for cross-report synthesis
- **Why:** Keep prompt governance isolated and versioned.
- **Deliverables:** `src/prompts/cross_report_synthesis/{system.yaml,user.yaml,...}` with dry-run fixtures.
- **Acceptance Criteria:** prompt hashes logged; fixture regression gate added.
- **Dependencies:** 0.2.

### Task 4.2 — Synthesis generator with provenance enforcement
- **Why:** Produce publishable narrative with strict claim evidence mapping.
- **Deliverables:** generator that consumes retrieval hits + signal ranks and emits bundle draft artifacts.
- **Acceptance Criteria:** each synthesized claim maps to >=1 source evidence reference; invalid output fails schema validation.
- **Dependencies:** 3.2, 4.1.

### Task 4.3 — Contradiction and uncertainty annotator
- **Why:** Top-tier cross reporting requires surfaced disagreement, not forced consensus.
- **Deliverables:** deterministic contradiction detector + narrative annotation fields.
- **Acceptance Criteria:** test corpus includes conflict cases and verifies explicit uncertainty blocks.
- **Dependencies:** 4.2.

## Phase 5 — Cross-report publishing

### Task 5.1 — Cross-report render contract + template
- **Why:** Separate rendering concerns from synthesis logic.
- **Deliverables:** render dataclasses + template/macros for cross-report layout (signals, consensus/divergence, source map).
- **Acceptance Criteria:** rendered artifact includes source trace section and machine-readable metadata.
- **Dependencies:** 4.2.

### Task 5.2 — WordPress publish integration for cross-report artifact
- **Why:** Operational delivery target is published portal content.
- **Deliverables:** publish generator/service extensions for cross-report post type or taxonomy route.
- **Acceptance Criteria:** publish idempotency proven; republish updates existing canonical post.
- **Dependencies:** 5.1.

### Task 5.3 — Cross-report publish orchestrator
- **Why:** Encapsulate sequencing/retries/state transitions.
- **Deliverables:** orchestrator with lifecycle states, retry/backoff, and notification hooks.
- **Acceptance Criteria:** pipeline test asserts retry counts, transitions, and final state.
- **Dependencies:** 5.2.

## Phase 6 — Search experience and discoverability

### Task 6.1 — Cross-report index/read APIs for UI + CLI
- **Why:** Operational and editorial users need queryable output.
- **Deliverables:** service/generator methods + CLI commands for searching bundles and evidence.
- **Acceptance Criteria:** filters and pagination tested; deterministic ordering.
- **Dependencies:** 1.3, 5.3.

### Task 6.2 — Streamlit/editorial surfacing
- **Why:** Manual review and intervention loop.
- **Deliverables:** UI pages for theme review, bundle draft inspection, signal breakdown, publish trigger.
- **Acceptance Criteria:** structured log events emitted for approval actions.
- **Dependencies:** 6.1.

## Phase 7 — Quality, safety, rollout

### Task 7.1 — Test matrix for cross-report stack
- **Why:** Prevent fake-green behavior in multi-stage pipelines.
- **Deliverables:** unit/integration/pipeline tests + fixtures for positive, edge, and failure paths.
- **Acceptance Criteria:** coverage + mutation thresholds met for new orchestrator/generator modules.
- **Dependencies:** phases 1-6.

### Task 7.2 — Observability pack and SLOs
- **Why:** Monitor synthesis quality and publish reliability.
- **Deliverables:** dashboards/queries for bundle success rate, theme-selection confidence, retrieval latency, publish success.
- **Acceptance Criteria:** runbook with alert thresholds and operator actions.
- **Dependencies:** 5.3.

### Task 7.3 — Progressive rollout plan
- **Why:** De-risk adoption.
- **Deliverables:** canary publisher set, shadow mode, quality gates, rollback strategy.
- **Acceptance Criteria:** exit criteria to move from shadow -> partial -> default documented and approved.
- **Dependencies:** 7.1, 7.2.

---

## 6) Explicit Non-Goals (This Phase)

1. Metric normalization across publishers/sources.
2. Unit conversion or statistical harmonization pipelines.
3. Financial-grade metric comparability scoring.

These can be future phases once cross-report synthesis and signal-centric publishing are stable.

---

## 7) Suggested Delivery Milestones

- **M1 (Foundation):** Phases 0-1 complete.
- **M2 (Intelligence):** Phases 2-3 complete.
- **M3 (Synthesis + Publish):** Phases 4-5 complete.
- **M4 (Productization):** Phases 6-7 complete.

Recommended implementation order is strict to minimize rework and keep contracts ahead of orchestration logic.
